# 知简 Hub

基于 Electron 的桌面应用工程骨架。当前只完成基础架构与工具链，未接入任何业务功能。

旧版 Web 实现（Next.js 15 + React 19）已归档，见标签 `v2.0-archive`；本项目不沿用其代码与功能。

## 技术栈

| 类别     | 选型                                      | 说明                                      |
| -------- | ----------------------------------------- | ----------------------------------------- |
| 运行时   | Electron 38.8.6（内置 Node 22.22）        | 主进程 CJS，预加载脚本 CJS                |
| 渲染层   | Vue 3.5 + Vite 7                          | `src/renderer` 为独立 Vite 根             |
| 状态     | Pinia 3                                   | 已接入，按功能建 store，不建全局大对象    |
| 语言     | TypeScript 5.9 严格模式                   | `vue-tsc --noEmit` 做类型门禁             |
| 数据     | SQLite（`node:sqlite`）                   | 零原生模块，无需 MSVC 工具链              |
| 样式     | CSS 变量 + scoped 样式                    | `tokens.css` 只放刻度，`theme.css` 放颜色 |
| 打包     | electron-builder 26                       | NSIS 安装版 + 便携版，仅 Windows x64      |
| 质量门禁 | Prettier + ESLint 9 + vue-tsc + node:test | 统一入口 `npm run check`                  |

## 目录结构

```text
src/
├── main/                  # 主进程（CJS）
│   ├── main.cjs           # 入口：路径 → 日志 → 数据库 → IPC → 窗口
│   ├── database.cjs       # SQLite 连接，schema 版本与迁移
│   ├── floor-plan-store.cjs # 户型图与房间的读写、校验、命令分发
│   ├── ipc.cjs            # 通道白名单 + 调用方校验
│   ├── logger.cjs         # 落盘日志，保留 5 份
│   └── paths.cjs          # userData 下的数据与日志目录
├── preload/               # contextBridge 暴露具名方法
│   └── preload.cjs
└── renderer/              # Vue 应用（Vite 根）
    ├── App.vue            # 全幅画板 + 悬浮窗口控件
    ├── app/types.ts       # 与主进程的契约（含命令联合类型）
    ├── components/        # 跨功能通用组件（FloatCard、RenameDialog）
    ├── features/floor-plan/ # 户型图画板（SVG 渲染）
    ├── lib/plan-geometry.ts # 墙段切分、门弧、窗线、八方向缩放的纯函数
    ├── stores/floor-plan.ts # 户型图与房间状态
    ├── assets/fonts/      # 随包分发的 woff2 字体
    ├── public/            # 原样拷进 dist 根的文件（字体授权全文）
    └── styles/            # fonts / tokens / theme / base
tests/                     # node:test 用例（几何、schema、存储规则）
design/                    # 界面语言与主题提案（theme-proposal.html）
```

依赖方向固定：`renderer → preload → main`，不反向依赖。渲染层拿不到 `ipcRenderer`，只能调用 preload 白名单里的具名方法；每个通道在主进程侧再校验调用者是否为当前主窗口主 frame。

## 布局：全幅画板 + 悬浮控件

界面里没有一条常驻的 header / footer / 侧边栏，打开就是一个铺满整个窗口的画板：

- `App.vue` 的 `.workspace` 用 `position: absolute; inset: 0` 占满窗口，`.canvas-wrap` 再 `inset: 0` 铺满它 —— 画布从窗口左上角一直到右下角，不预留标题栏高度。
- 品牌印章与三个窗口按钮改成右上、左上的两个「小岛」（`.brand` / `.windowControls`），整条 `.chrome` 容器 `pointer-events: none`，只有小岛 `auto`，中间留白仍然属于画布。可拖拽区域**只**是 `.brand` 那一块，所以画布中上部也能正常拖拽绘图。
- 画板之上的控件全部绝对定位：顶部居中搜索框 `.float-search`、左上菜单列 `.rail-left`（首页 / 房间 / 家具 / 储物 / 导出）、底部居中绘图工具 `.float-toolbar`（仅修改模式，浮在左下底栏之上）、**左下一条精简底栏 `.float-dock`**、**右下单独的缩放条 `.float-zoom`**。
- 底部刻意拆成左右两半，都只贴边、按内容收缩，中间一大片留给画板：左下底栏只有三样东西——图纸角标（编号 + 图名 + 指北针）、图层开关（尺寸 / 材质 / 网格，做成一段分段控件而不是三个复选框）、比例尺；右下单独一条只有缩放（− % + | 适应画布）。两半互不牵连，高度都压到 34px（原来一条居中底栏要 46px 且横跨半个屏幕）。
- 默认选中**首页**：这时右侧什么都不弹，界面上只剩画布、顶部搜索和左侧菜单。首页的关闭按钮就是「回到什么都不弹的状态」，再点一次已选中的菜单项也能回首页。
- **浏览态的成图是一张干净的底图**：不画房间名、不画面积、也不拉侧边尺寸链 —— 只有墙、门窗、柜子方块。首页、三个清单页（房间 / 家具 / 储物）、以及在房间菜单里选中某一间看内容，都属于浏览态。**只有进入修改模式**才把房间名、面积和毫米尺寸链画回来；尺寸链还要再与底栏的「尺寸」开关求与。判断集中在 `showRoomLabels = mode === 'edit'`，经 `plan-drawing.vue` 的 `labels` prop 下发。理由：浏览态回答的是「东西在哪」，文字压在柜子方块上反而看不清；需要知道「这是哪一间、多大」的只有改图的时候。
- 顶部搜索一次搜三样东西：物品、储物设备、房间。输入即出下拉（完全相同 > 前缀 > 包含，同档内物品优先于柜子、柜子优先于房间，最多八条），`Enter` 取第一条，`Esc` 清空，`Ctrl/⌘ + K` 任意时刻聚焦。命中后按类型分派：物品 → 定位到它所在的房间并让它在清单里闪一下；柜子 → 打开这个柜子的内容；房间 → 选中并适应视口。
- 窄窗（< 1180px）隐藏工具按钮文字、搜索框快捷键，比例尺横线最多 90px；再窄（< 940px）整块收起图纸角标，图名在左侧菜单里已经能看到；矮窗（< 720px）只收留白，画板尺寸始终不被压缩。
- 比例尺不写死「1 m」：横线长度 = `60 * zoom`（60px = 1 m），缩到 20% 时 1 m 只有 12px，读不出来。`scaleBar` 从 0.5 / 1 / 2 / 5 / 10 / 20 m 里挑一个让横线落在 60–150px 的档位，横线和文字一起变。

## 窗口与标题栏

窗口以 `frame: false` 启动，系统边框与 min / max / close 全部关闭，改由 `App.vue` 自绘：

- 没有标题栏这一行；`.brand` 小岛声明 `-webkit-app-region: drag` 作为唯一的拖拽把手，窗口按钮 `no-drag`；Windows 下的双击最大化、贴边缩放由 `thickFrame` 保留。
- 三个按钮通过 `zhijian:windowControl` 回调主进程，`zhijian:windowState` 查询当前最大化状态，最大化 / 还原后主进程推送 `zhijian:windowStateChanged` 让图标切换。
- 关闭走 `window.close()` 而不是销毁，保留 `close` 与 `pagehide` 钩子，便于以后接「退出前保存」。

## 主题

当前主题为 **苔痕 · 竹青**：竹青 `#3f5a2a` 作主色，赭石 `#8a5a2b` 作次强调，朱红 `#b03a2e` 只用于危险操作。全部颜色集中在 `src/renderer/styles/theme.css`，`tokens.css` 只放刻度（间距、字号、圆角、标题栏高度、网格尺寸）。

另外三套候选主题（宣纸·朱砂 / 墨夜·朱砂 / 檀木·赭石）保留在 `design/theme-proposal.html`，可直接在浏览器里打开对比，将来要做暗色模式或换肤时从这里取色。

## 字体

全站统一使用 **霞鹜文楷 · 屏幕版**（LXGW WenKai Screen），随包分发，不依赖用户机器是否装过 —— 桌面应用必须字体自足，否则同一份界面在不同电脑上排成两副样子。

- `src/renderer/assets/fonts/` 放两份 woff2（Regular 9.8 MB / Medium 8.7 MB），`styles/fonts.css` 里用 `@font-face` 声明同一个家族 `'LXGW WenKai Screen'`，字重区间分别为 `300 400` 与 `500 700`。
- `fonts.css` 必须在 `tokens.css` / `theme.css` 之前导入（见 `base.css` 顶部），保证主题令牌引用该家族时字体已注册。
- `theme.css` 里 `--font-serif` / `--font-sans` / `--font-mono` 三个令牌全部以该家族打头，后面的系统字体只作加载失败兜底。文楷数字等宽（0.6em），所以面积、尺寸、房间编号等等宽场景也直接用它，不再引 Consolas。
- 全局关掉 `font-synthesis`：只有 400 / 500 两档真字重，600 / 700 落到 Medium。合成假粗体会把楷书笔锋糊成一团，宁可停在 Medium。
- 唯一需要写死字体栈的地方是 `features/floor-plan/plan-drawing.vue`：图纸 SVG 会被序列化导出成独立文件，导出后没有 CSS 上下文，字体只能写在元素属性上，所以那里是行内 `font-family` 而非 CSS 变量。
- 授权 SIL OFL 1.1，全文在 `src/renderer/public/OFL-LXGW-WenKai.txt`，构建时原样拷进 `dist/renderer` 根目录随安装包发布。附加条款只允许转换后的 woff2 作网页字体使用，不能再单独发布成可安装桌面字体；当前用法（仅被 `@font-face` 引用）符合要求。

## 浏览模式与修改模式

默认落在**浏览模式**：这是「查储物位置」的应用，打开就该能搜、能点、能看，不该一上手就在改图。

- 浏览模式下画布只做三件事：拖动平移（滚轮缩放、空格或中键也行）、点房间选中、顶部搜索定位。选中的房间用一圈虚线标出来（虚线就是唯一的「选中」语言，别处不再出虚线）；没选中的房间不描边，鼠标压上去只给一条很淡的实线当「这里能点」的提示。柜子同理：选中时自带一圈虚线描边。整圈虚线比粗实线轻，不会把屋里的柜子方块和房间名压住。
- 点房间或柜子，右侧弹出的卡片只回答一个问题——**里面有什么**：顶部是名称与「一共 N 件物品」，下面就是物品清单（超出在卡片内滚动）。卡片从左侧菜单的顶边起、撑到画板底部，与菜单顶端对齐，高度是浏览态的最大可用值。没有输入框、没有柜子清单。**首页上点房间是纯浏览，卡片里不出现任何修改操作**；从「房间 / 家具 / 储物」清单点进去看内容时，卡片底部才出现「修改这个房间」，点一下直接进这一间的编辑态。
- 点左侧「首页」等于彻底收工：清空选中、关掉所有卡片，正在修改时**连修改模式一起退出**（工具栏、属性卡、房间标注全部收起），回到只有画布、搜索与菜单的状态。
- 改户型必须先显式进入**修改模式**。入口有两个，都在「房间」这条线上：房间清单每一行行尾的修改按钮，以及房间内容卡底部的「修改这个房间」，点哪一个是哪个房间直接进属性卡（不必先进模式再找房间）。也可以按 `E`。左栏刻意不摆常驻的修改开关 —— 这个应用默认是「看」，改是例外动作。进入后才出现绘图工具（房间 / 门 / 窗 / 平移）、八方向缩放柄、可编辑的房间属性与删除按钮；退出点工具条最右边的「完成」。
- 选了任一绘图工具（房间 / 门 / 窗）会自动进入修改模式——选工具本身就是「我要改」的表示，不用先点开关。
- 撤销重做、`Ctrl+Z` 等只在修改模式下生效；浏览模式下键盘只留 `E`、`0`（适应画布）、`Esc`（清空选中）与 `Ctrl/⌘ + K`（搜索）。
- 画布上的储物设备（柜子 / 架子 / 收纳箱 / 家具）同样只在修改模式里增删：浏览模式下点它只是「打开看看里面有什么」，位置由 `lib/plan-storage.ts` 按房间自动铺网格，不做自由拖拽——这个应用要回答的是「东西在哪」，不是家具摆放模拟器。
- 拆墙也在修改模式里：房间属性卡的「打通」列出这个房间**真的贴着邻居**的边，点一下就把那条边整面拆掉，两侧地面直接连通（同一面墙只有一条，一侧拆掉隔壁就通了）；四周没有邻居的房间不列任何可选项。
- 修改模式下的「加柜子」「登记物品」两个表单挂在房间属性卡片里；删除柜子或物品是行尾的小垃圾桶按钮，两个表单区都用虚线隔开，避免删除键紧挨着新增键被误点。

## 户型图

户型图是整个数据模型的根：家里的一切（家具、储物设备、物品）最终都要落在房间上，所以首次进入必须先建图，没有图时画布只显示创建引导。

**数据模型（schema 版本 9）**

| 表           | 说明                                                                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `floor_plan` | 单套户型，`CHECK (id = 'singleton')` 在库层锁死只有一行；`room_seq` 是房间默认名称序号                                                        |
| `rooms`      | 房间矩形：`id`、`name`、`x`、`y`、`width`、`height`、`floor`、`outdoor`、`open_walls`；坐标为画板绝对坐标                                     |
| `openings`   | 墙上的洞口：`kind`（door/window/bay）、`wall`（四面墙）、`pos`（沿墙起点）、`width`、`hinge`、`swing`（门的开向 in/out）、`depth`（飘窗进深） |
| `storage`    | 储物设备：`room_id`、`name`、`kind`（cabinet/shelf/box/furniture）、`sort_order`                                                              |
| `items`      | 物品：`room_id`（必填）、`storage_id`（可空）、`name`、`category`、`quantity`、`note`                                                         |

洞口不存绝对坐标，只存「挂在哪面墙、沿墙第几个像素开始、多宽」。房间移动或缩放时洞口自动跟随，不会出现门窗跑到墙外的情况。房间删除时洞口级联删除。

物品的层级是「房间 → 储物设备 → 物品」，但 `items.room_id` 是**必填**的：物品一定在某个房间里，这是「搜到就能去拿到」的底线。`storage_id` 可空，删柜子用 `ON DELETE SET NULL`，物品留在原房间不会凭空消失。

`rooms.outdoor` 为 1 表示户外空间（阳台 / 露台）。阳台**不另立一张表**：它在平面上仍是一个矩形房间，改的只是画法 —— 不与别室共用的那几面墙砌成栏杆（厚度 100 mm），与室内共用的那面仍是 120 mm 实心隔墙。这样阳台的移动、缩放、改名、开门窗、放柜子全部原样复用，不需要第二套逻辑。版本 5 的迁移就是给 `rooms` 加这一列，默认 0，旧图升上来一律是室内。

飘窗同理不新建表：它是第三种洞口 `kind = 'bay'`。平面上就是一个墙洞 + 向室外凸出的窗台，位置、宽度、进深、沿墙拖动全部复用现有的洞口机制：宽度默认 120px（比普通窗宽，窄了就不像能坐人的窗台），进深存在 `openings.depth`（像素），默认 26px（约 430 mm），可在属性卡里按毫米调到 200–1000 mm。**飘窗只能开在外墙上**：隔墙两侧都是室内，凸出去的窗台会正好长在隔壁房间里，所以 `bayFits()` 用窗台矩形的真实几何和其余房间求交，相交就拒绝摆放（预览转成警示红并提示原因）；改进深时同样用 `bayFits()` 试算一遍，会长进隔壁房间的进深直接拦下并说明。普通窗不受这条限制，室内窗、垭口照样能开在隔墙上。

`rooms.open_walls` 存的是「哪几条边不砌墙」，逗号分隔文本（`top,left`，空串＝四面墙都在）。拆墙**不复用门窗**：门窗是在墙上凿一个洞，洞两侧还得留墙垛与墙的厚度；拆墙是整条边一个洞都不剩，几何上完全不同，硬塞进 `openings` 会把「洞口」和「没有墙」两种语义搅在一起。存成一份集合而不是四列布尔，是因为拆掉的边天然就是个集合，以后要支持斜墙也不用再改表结构。

拆墙还带一条不可回避的物理事实：**一面墙只有一个**。所以拆墙不区分是谁拆的 —— 只要一侧宣布拆掉，这一段墙体就不存在了，隔壁自然连通；反过来只拆一半会让邻居家里立着一堵看不见对面的墙，「打通」等于没打通。界面上因此只列出**真的贴着邻居的边**（`connectableWalls()`）：朝室外的边拆掉只是把家开个口子，那叫漏风不叫连通，想要那个效果应该开门或开窗。同一条边上原本画着的门窗只是**藏起来、不删除**：拆墙不动 `openings` 里的数据，把墙补回来门还在。判断「这面墙还在不在」统一走 `wallIsOpen()`，它把全屋的 `open_walls` 都看一遍 —— 一面墙只有一个，邻居拆了，自己挂在这面墙上的门窗同样会悬空，只看自己那一间会漏。门窗清单里这类洞口会标上「墙已拆」，免得用户以为东西丢了。

`rooms.floor` 为 `NULL` 表示按房间名自动推断地面（卧室木地板、厨卫小砖、其余大砖）；用户手动选过之后写入具体值，此后改名不再影响地面。可选材质共十种：`wood`（橡木）、`tile`（大砖）、`small`（小方砖）可被推断，`walnut`（胡桃木）、`diagonal`（斜铺木）、`subway`（长条砖）、`marble`（大理石）、`terrazzo`（水磨石）、`microcement`（微水泥）、`carpet`（地毯）只能手动指定。新增材质要同时改 `floor-plan-store.cjs` 的 `FLOORS`、`app/types.ts` 的 `FloorMaterial` 与 `plan-drawing.vue` 的 pattern。

单套户型是明确的产品决策，不是临时实现——多套或多楼层需要新增一层实体，届时走新的迁移。

**绘图与编辑**

- 工具分开：`V` 选择、`R` 画房间、`D` 放门、`W` 放窗、`B` 放飘窗、`H` 平移。房间工具下拖出轮廓，选择工具下拖动和八方向缩放。
- 内部沿用 **60px = 1 米** 的坐标，与旧图兼容；编辑按 **100 mm** 网格吸附，优先吸附相邻房间的墙体中心线。绘图背景每大格为 1 米。
- 右侧悬浮卡片里直接输入房间宽度、进深，或门窗宽度、距墙起点的偏移，单位统一为 **mm**；飘窗再多一个「向外出挑」，同样是 mm，范围 200–1000 mm。房间短边至少 1000 mm，门窗至少 400 mm。
- 选择门窗工具后点击墙面放置；预览展示真实落位。选择工具下拖动门窗沿墙调整位置。平开门的姿态由两个独立开关决定：**开向**（内开 / 外开）与**门轴**（洞口起点 / 终点），在门窗属性卡里各是一组胶囊，点一下就能看到当前是哪种。
- 新绘制、移动和缩放时阻止房间重叠；缩小时保留门窗边界。主进程再次校验同一物理墙上的洞口冲突，失败则事务回滚。
- 滚轮以指针为中心缩放；空格拖拽或鼠标中键平移；`0` 适应画布；`Esc` 取消当前拖拽并恢复已保存状态；`Delete` 删除选中的房间或门窗。
- `Ctrl+Z` 撤销、`Ctrl+Shift+Z` / `Ctrl+Y` 重做，保留当前会话最近 50 次操作。撤销重做也会落库；重启后保留最后图纸，历史不跨会话。
- 修改模式下选中房间时右侧自动弹出「房间属性」卡片；左侧菜单的「房间」列出全部空间，点任意一项先看里面存了什么。尺寸、材质、网格可以分别开关，默认显示简洁建筑线稿。底栏的「尺寸」按钮只控制毫米尺寸链，房间名与面积跟随「是不是首页」自动显隐。
- 空图可载入两室一厅示例（含过道、玄关和阳台）；已有房间时不提供覆盖入口。支持导出独立 SVG 图纸。
- 左侧四个菜单项各管一件事：**首页**收起所有卡片；**房间**列全部空间（面积、门窗数、里面几件东西）；**家具**只列 `kind = furniture` 的设备；**储物**列全部储物设备。清单里的每一行点进去就是「这个房间 / 这个柜子里有什么」的实物清单，物品行再点一下就把视线拉到它所在的柜子并闪一下。
- 左栏只留四项菜单加一枚「导出」。修改的入口在房间清单与房间内容卡上（见上）；图纸概览的入口在左下底栏的图纸角标上，点一下开合那张概览卡片。

**几何与渲染分层**

- `plan-geometry.ts`：墙面参考系、门弧、窗线、八方向缩放等基础纯函数。
- `plan-scene.ts`：按物理墙线汇总房间边界，在 T 形交接处切分；共享墙只绘制一次，再统一减去门窗洞口。墙端延长只发生在转角，不能侵占洞口。
- `plan-drawing.vue`：纯 SVG 图纸，画布与导出共用。墙体不再画成线，而是按墙厚铺成**实体矩形**，再按「整组并集」上光影：
  ① 先把所有墙矩形收进同一个 `<g>`，共享一次高斯模糊做右下偏移的投影（阴影连成一片，不是每段各糊各的）；
  ② 墙身仍放在同一个 `<g>` 里，用一枚 `feDiffuseLighting` **浮雕滤镜**沿整组墙的外缘算明暗——光从左上方来，上沿 / 左沿亮、下沿 / 右沿暗；
  ③ 共用隔墙（`shared`）另铺一层略深的 `#ccd4c5`，让两户之间读得出分界。
  **关键：任何一段墙都不描边。** 一段一段描边必然在拐角和丁字形接口叠出两三条互不相干的深色线，这就是「多余黑线」的来源；浮雕的明暗只跟着整组图形的最外轮廓变化，接缝内部是平的，天然没有边。外侧墙示意厚度 240 mm，共用隔墙 120 mm。
- 门窗洞口先铺**进深底色**（门洞偏亮，因为门槛是能走过去的地面；窗洞偏冷灰，像水泥断面），再补两侧墙垛断面。门扇画成有厚度的板（`leafBoxOf` 把铰链到门扇端点换算成细长矩形）并带自己的模糊投影，保留开启弧与铰链点；窗是斜向高光玻璃（`plan-glass` 渐变）+ 三线窗棂 + 端框。门扇伸向哪一侧只看 `swing`：`doorGeometry` 拿到的墙面法向 `n` 一律指向室内，外开就把 `n` 取反（`sign = swing === 'out' ? -1 : 1`），圆弧由 `arcPath` 按三点角差自动翻 sweep，不需要为四种「开向 × 门轴」组合各写一套。外侧显示毫米尺寸链。
- **飘窗**（`bayGeometry`）：墙洞按窗宽切开，再向室外凸出 `opening.depth` 的窗台（每个飘窗自己的进深，默认 `BAY_DEPTH = 26px` ≈ 430 mm，`bayDepth()` 负责把脏值夹到 12–60px）。因为进深是可变的，玻璃带宽度也跟着取 `min(6, 正面宽/6, 进深/3)`，进深调到最浅时三条线也不会挤成一条。画法照真实户型图的线稿语言，只有三层：① 台面 `sill`——一整块极浅的铺装色 `#eef1e8`，边界就是窗线内侧，没有任何厚框；② 三线窗 `panes`——每一面玻璃画三条平行细线，带子深度 `BAY_GLASS_BAND = 6px`（约 100 mm），颜色两侧 `#4c7681`、中间 `#7fa3ab`，线宽 0.8px；③ 台面内侧一条 `#7a876a` 虚线（`4 3`）`sillEdge`，表示窗台板是出挑的。**三条线不是三面各画三条（共 9 条），而是三条同心 U 形折线**：每一笔从墙面向外、横过正面、再回到墙面，一条线的两个端点落在同一侧的墙线上。原因很实在——三面各画三条互不相干的线，拐角处每条都各自收头，于是每个转角都留一个豁口；同心折线在转角共用同一个顶点，天然闭合。为什么不用「窗框 + 角柱 + 中梃」那套有厚度的色块：那是立面效果图的画法，放进平面图会把台面压成一个小方块、和满图的细线不是一套；三条平行线才是图纸上表示玻璃的标准画法。放置前用 `bayFits()` 校验窗台不压到别的房间，落点不合法时预览整体转成 `var(--danger)`、半透明填充用 `--danger-soft`，点下去只出提示不写库。属性面板与门洞列表里的名字统一走 `openingLabel()`（平开门 / 标准窗 / 飘窗）。
- **阳台栏杆**：`buildWalls` 给每段墙多带一个 `outdoor` 标记 —— 只有「不属于任何共用墙、且两侧房间都是户外空间」的墙才算栏杆。栏杆不进墙体的并集浮雕组（`solidWalls` 过滤掉了），照真实户型图画成**两条平行细线 + 密排短刻度**：底 `#eef1e8`、外沿线 `#bfcaab` 厚 `RAIL_FACE = 1.25px`、内沿线 `#7a876a` 厚 `RAIL_INNER_LINE = 0.8px`，两条线之间按 `RAIL_TICK_GAP = 6.4px`（约 107 mm）打一道 `RAIL_TICK = 0.85px` 宽的立柱刻度（`#858d75`，不透明度 0.7）。**拐角是让出来的，不是盖上去的**：某一段的端点若探到一段与它垂直的相邻栏杆，内沿线就缩进 `across - RAIL_INNER_LINE`（留 0.8px 重叠防发丝缝），让它停在对方的内沿线上，两条内线永远不互相穿插；端柱（`#7a876a` 的 5×5 实心块）只在该端**完全没有邻居**时补，也就是贴实心墙或落在阳台开门缺口两侧的位置。原则是：栏杆只给两条线和刻度，不上色阶、不打高光、不画粗扶手 —— 那套属于效果图，在灰绿线稿里会显得像打了光的金属，反而抢戏。这样栏杆既不会跟墙体一起被浮雕成一道厚墙，也不会在拐角冒出黑线或留下豁口。
- 画布上的柜子方块同样补了一层右下偏移的淡影，方向和墙体一致，看起来才是摆在屋里的一件东西。
- 地面质感是三层叠出来的：① `<pattern>` 按 60px = 1m 的真实尺寸定义铺装（不是屏幕像素密度，缩放画布时纹理跟着一起放大）；② `plan-light` 线性渐变做左上到右下的光照；③ `plan-ao` 内阴影（模糊描边）做墙脚环境遮蔽。后两层只在打开材质时渲染，纯线稿模式不受影响。
- 十种铺装：橡木 / 胡桃木（板宽 150 mm、板长 1 m 错缝，板面用渐变做明暗，`<g>` 板组被三个木纹 pattern 复用，斜铺靠 `patternTransform` 旋转）/ 大砖 800 / 长条砖 300×150 错缝 / 小方砖 300 / 大理石 800 大板带跨板石纹 / 水磨石 0.4 m 石粒 / 微水泥无缝只靠抹痕色差 / 地毯细密交叉绒线。房间名与面积压白色描边上（`paint-order: stroke`），纹理再花也不会吃掉文字。
- `use-plan-editor.ts`：画布坐标换算、缩放平移、命中、吸附和拖拽状态。拖动预览独立于已保存数据，取消和写入失败都不会污染存档。
- `floor-plan.ts`：IPC 保存状态与撤销重做。命令先转换成普通数据，避免 Vue 响应式代理跨 `contextBridge` 时无法克隆。

房间仍使用矩形与墙体中心线尺寸，不支持任意多边形或斜墙。墙厚是绘图示意，不区分承重属性；面积为中心线范围统计，不作为套内净面积或建筑面积。

阳台只是一个矩形房间加一个标记，所以「L 形阳台」「弧形阳台」需要拆成两个矩形去拼；飘窗只向一侧凸出，不支持转角飘窗或斜角出挑，也不能开在隔墙上（那会把窗台长到邻居家）。

**写入路径**：渲染层发送语义命令，主进程校验并返回完整快照。`replace-rooms` 用于示例和历史恢复：在事务内完整校验所有房间、材质、门窗、储物设备与物品，任一数据无效则整次回滚。储物与物品另有 `add-storage` / `rename-storage` / `remove-storage` / `add-item` / `update-item` / `remove-item` 六个命令，校验项包括 `kind` 枚举、数量为正整数、备注长度上限，以及「选的柜子必须在这个房间里」。房间命名序号只增不减，撤销不会回收。版本 4 的迁移只建新表，旧图直接可用；版本 5 给 `rooms` 加 `outdoor` 列，默认 0，旧图升上来全是室内；版本 6 重建 `openings` 表把 `kind` 的 `CHECK` 放宽到含 `bay`（SQLite 改不了 CHECK，只能建新表搬数据，老的 `door` / `window` 原样保留）；版本 7 给 `rooms` 加 `open_walls` 列，默认空串，旧图升上来四面墙都在；版本 8 给 `openings` 加 `swing` 列（`in` / `out`，带 CHECK），旧图升上来一律内开。这次用 `ADD COLUMN` 而不是重建表：重建表是为了改已有 CHECK 里的枚举（版本 6 那次），而 `swing` 是随新列一起新建的约束，加列就能带上；版本 9 给 `openings` 加 `depth` 列（REAL，默认 26），也是 `ADD COLUMN`——它只是一个数值、不是枚举，不需要重建表。拆墙走独立命令 `set-room-open-walls`，传的是**整份集合**而不是「拆一条 / 补一条」：界面上的四个开关本来就是一份完整状态，整体替换才不会出现前后端各自以为自己知道当前值的情况。已经拆掉的边不能再放门窗：`add-opening` 在主进程里也查一遍 `open_walls`（同样跨房间判断），因为那段墙已经不存在了，放行只会在库里多一个看不见的洞口。

**撤销快照**：一次撤销存的是三张表的同一时刻画面（`rooms` + `storage` + `items`），否则撤销一次房间改动会把期间登记的物品一起抹掉。

## 接入新功能时的约定

1. 先在 `database.cjs` 的 `MIGRATIONS` 追加版本迁移，`SCHEMA_VERSION` 同步 +1；不提前建空表。
2. 新增 IPC 通道：`ipc.cjs` 加通道 → `preload.cjs` 加具名方法 → `renderer/app/types.ts` 加契约类型，三处必须同时改。
3. 渲染层不直接访问文件系统与数据库，所有读写走 IPC。
4. 完成标准为 `npm run check` 通过；涉及主进程改动再跑一次 `npm run smoke`。
